# TwinForge Studio — Workflow Studio Audit
_Phase 1 deliverable. Generated by repository inspection._

_Audit refresh: 2026-10-15. The verified corrections below supersede stale claims in the original map._

## Current verified state

- Seed-loop persistence is already represented in `backend/prisma/schema.prisma`: `WorkflowRun`, `SeedDataset`, `SeedRecord`, `LoopIteration`, and `ExecutionLog` are present. Do not add duplicate models.
- `backend/src/workflow/seed.service.ts`, `seed.router.ts`, and `loop-execution.service.ts` implement tenant-scoped dataset/loop APIs and persisted results. However, `SeedRouter` is not mounted in `backend/src/trpc/trpc.router.ts`, so these procedures are currently unreachable through the assembled API.
- `backend/src/queues/loop.processor.ts` and the queue service provide a BullMQ worker path. The service's `maxRetries` and `backoffMs` are accepted but not applied; `strategy: 'batch'` changes the fetched batch size but records are still processed serially. Do not expose these as working retry/backoff/parallel controls.
- The `/twinforge` overview at `app/(dashboard)/twinforge/page.tsx` imports `DEMO_PORTFOLIO` and maps local `DEMO_*` constants into production UI. This remains a static dashboard, not a data-backed studio.
- The current `/brokerage/workflow-studio` page at `app/(dashboard)/brokerage/workflow-studio/page.tsx` mounts `components/workflow-studio/WorkflowStudio.tsx`, not the React Flow `workflow-studio.tsx` entry mapped below. It supplies no persisted workflow, executor, or loop dataset.
- The React Flow studio's `components/workflow-studio/lib/trpc-executor-client.ts` is wired to the JKDM integration surface, not to workflow save/run/history. Its `getExecution` currently fabricates a terminal success response; it must not be used as execution progress.
- `components/workflow-studio/types/workflow.ts` starts with `@ts-nocheck`; strict typing is not currently satisfied in that type surface.

### Immediate implementation targets

1. `backend/src/trpc/trpc.router.ts` — mount the existing `SeedRouter` under the existing orchestration surface and ensure its providers/modules are registered.
2. `backend/src/workflow/loop-execution.service.ts` — make run creation idempotent by deterministic request identity, and implement or reject retry/backoff/strategy options truthfully; make cancellation/fail-fast terminal iteration counts consistent.
3. `components/workflow-studio/` — connect the React Flow editor to persisted workflow procedures and the seed-loop API; remove fabricated execution polling from this path.
4. `app/(dashboard)/twinforge/` — replace production `DEMO_*` view data with tenant-scoped queries and explicit empty/error states; retain fixtures only in development/test.
5. `docs/workflow-studio-audit.md` — keep this map synchronized with implemented wiring and test coverage.

## 3. Persistence Layer

### Frontend Prisma schema (`prisma/schema.prisma`)
Minimal — only `User`, `Tenant`, `Session`, `VerificationToken`, brokerage models (`Accreditation`, `Client`, `Declaration`), digital-twin models (`Zone`, `TwinNode`, `TwinEdge`, `Scenario`, `Run`, `TwinEvent`, `TwinAgent`, `AgentRun`, `Policy`), and `AuditEntry`.

**No `Workflow`, `WorkflowRun`, `SeedDataset`, `SeedRecord`, `WorkflowExecution`, `LoopIteration`, or `ExecutionLog` models.**

### Backend Prisma schema (`backend/prisma/schema.prisma`)
Production schema. Contains:
- `Workflow` — `(tenantId, workflowId, version)` unique, `definition: Json`, `active: Boolean`
- `WorkflowRun` — `status: WorkflowRunStatus`, `input/output/error/steps: Json`, `startedAt/endedAt`, optional seed dataset, loop config, idempotency key, and aggregate counters
- `WorkflowRunStatus` enum — `QUEUED | RUNNING | SUCCEEDED | FAILED | AWAITING_APPROVAL | CANCELLED`
- `TwinScenario` / `TwinRun` / `TwinMetric` — digital twin simulation runs
- `Job` — generic job queue table (`queue`, `name`, `status`, `payload`, `attempts`, `maxAttempts`)
- `DomainEvent` — event bus table

Also present: `SeedDataset`, `SeedRecord`, `LoopIteration`, and `ExecutionLog`. The missing work is API registration and correctness/coverage, not adding another persistence layer.

### tRPC router (backend)
`customAgents.orchestration` is assembled in `backend/src/trpc/trpc.router.ts`; the existing orchestration router exposes:
- `listWorkflows` — list workflows by tenant
- `getWorkflow` — get workflow + definition
- `saveDraft` — upsert workflow definition
- `validate` — server-side validation
- `execute` — synchronous execution (returns steps inline)
- `listRuns` — paginated run history
- `getRun` — run detail with steps

`SeedRouter` defines `listDatasets`, `getDataset`, `createDataset`, `addRecords`, `startLoop`, `listLoopRuns`, `getLoopRun`, and `cancelLoopRun`, but is not included in the assembled router. The legacy `execute` remains synchronous; the loop path is queued when reachable.

## 4. Execution Infrastructure

### Queue / Worker
- `bullmq` v5 and `ioredis` v5 are dependencies.
- `backend/src/queues/queue.service.ts`, `queues.module.ts`, and `loop.processor.ts` implement the BullMQ queue path for workflow loops (`cfs:workflow-loop`).
- `backend/src/workflow/loop-execution.service.ts` enqueues one batch at a time and persists progress, iterations, and logs.
- The `Job` model exists, but this loop path uses BullMQ rather than that DB-backed model.
- The current worker does not implement configured retry/backoff or concurrent batch execution; interruption recovery/claim ownership also needs verification before production guarantees are made.

### Real-time
- `socket.io` + `socket.io-client` in `package.json`
- `providers/SocketProvider.tsx` exists
- No SSE route found for execution progress

## 10. Summary

The repository has a **fully built React Flow studio** (`workflow-studio.tsx`) that is never mounted. It has a **complete tRPC execution router** (`customAgents.orchestration`) that runs synchronously. It has **no seed-loop domain model** (no `SeedDataset`, `SeedRecord`, `LoopIteration`). The TwinForge dashboard renders entirely static demo data.

The implementation plan is:
1. Mount and wire the existing seed-loop API and backend module dependencies.
2. Correct idempotency, retry/failure/cancel semantics in the existing loop service and worker.
3. Bind the React Flow editor and TwinForge views to persisted workflow, dataset, run, iteration, and log queries.
4. Add focused backend integration tests for tenant isolation and loop lifecycle, then update this map with verified coverage.
4. Mount new studio on brokerage page with real data
5. Wire TwinForge pages to real `TwinScenario`/`TwinRun` data
6. Add dev fixtures and tests
